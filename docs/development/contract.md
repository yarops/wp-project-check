# Контракт скилла

Документ описывает, что скилл делает и по каким правилам. Источник истины для агента — `SKILL.md` и `references/`. Этот документ их резюмирует для разработчика. Если они разойдутся с ним, поправить нужно документ.

## Назначение

Проверка технической корректности кодовой базы WordPress-проекта и соблюдения формальных требований языка, платформы, API и технических соглашений, зафиксированных в репозитории. Предрелизная проверка — один из режимов; в разработке можно запускать отдельную область или охват.

Вне охвата: бизнес-логика, полнота фич, соответствие продуктовой задаче, требования каталогов публикации (включая WP.org), специализированные профили плагинов и тем.

Скилл только ревьюит и пишет отчёт. Исходники и конфигурацию проекта не изменяет, дефекты не исправляет.

## Файлы

```text
wp-project-review/
├── SKILL.md                  # параметры, порядок работы, области, общие правила, завершение
├── references/
│   ├── project-context.md    # сбор контекста: target, границы кода, основания, охват
│   ├── tooling.md            # инвентаризация, допустимые команды, TOOL-CHK, сводка запусков
│   ├── security.md           # реестр точек входа, проверки по типам, SEC-CHK
│   ├── reliability.md        # REL-CHK: контракты, ввод, ресурсы, механизмы с состоянием, повторы
│   └── reporting.md          # классификации, структура отчёта, шаблон находки, самопроверка
└── scripts/
    └── report-html.py        # Markdown-отчёт → автономный HTML (stdlib)
```

Сначала агент загружает только `SKILL.md`. Reference области читается при её запуске, `reporting.md` — перед выдачей отчёта.

Новая область появляется вместе со своим reference. Описание области в документации не означает, что она реализована.

## Параметры

| Параметр | Значения | По умолчанию |
|---|---|---|
| `scope` | `{type: diff, base}` / `{type: feature, subject}` / `{type: global}` | `{type: global}` |
| `areas` | `tooling`, `reliability`, `security` | все реализованные |
| `target` | `plugin` / `theme` / `site` | по признакам кодовой базы |

Запрос на естественном языке переводится в те же параметры. Уточняются только существенные неоднозначности. Явные `scope` и `areas` ограничивают проверку.

Параметра окружения нет. Сценарии, запросы к endpoint и WP-CLI на работающем сайте не выполняются, в том числе для подтверждения находки.

Прошлый отчёт не является базой сравнения кода; повторная проверка закрытия находок не поддерживается.

## Области

| Область | Предмет | Результат |
|---|---|---|
| `tooling` | Команды проекта, CI, линтинг, статанализ, зависимости, изолированные тесты | Результаты инструментов, фактический охват запусков |
| `security` | Точки входа, права, владение объектами, потоки данных, неявные защиты платформы | Находки и реестр проверенного охвата |
| `reliability` | Обработка ошибок и ввода, контракты API, ресурсы, механизмы с состоянием, повторы и частичные отказы | Нарушения контрактов и инвариантов с основанием |
| `architecture` | не реализована | — |
| `operations` | не реализована | — |

Запрошена нереализованная область — скилл сообщает об этом и не подменяет её. Запрошены только нереализованные — работа завершается уведомлением без отчёта.

## Порядок работы

1. **Контекст.** Объект и признаки, границы собственного кода, технические правила и соглашения репозитория, доступные доказательства (CI, тесты, конфигурация инструментов), охват. Для `global` — полный перечень файлов без усечения; файлы кода, не прочитанные ни в одной области, перечисляются в ограничениях.
2. **План.** Запрошенные области сверяются с реализованными. Для каждой выбираются применимые проверки с основанием и способом, неприменимые отмечаются с причиной. В план входят механизмы с состоянием (`reliability`) и пути вывода защищаемых данных (`security`). Охват расширяется только из-за новой находки или зависимости, с записью причины.
3. **Проходы.** `tooling` → `security` → `reliability`. Команды запускаются только в `tooling`.
4. **Разбор кандидатов.** Одна причина — одна находка. Для каждого кандидата проверяются предпосылки, достижимость и последствия. Затем проход на опровержение:
   - для находки — защита выше и ниже по пути;
   - для «пройдена» — не основан ли вывод только на успешной ветке;
   - для повтора — что меняется до следующей попытки;
   - для записи — что получат вызывающий код и следующий шаг при отказе.
5. **Отчёт.** Покрытие сверяется с планом; если доступная работа осталась, проход продолжается. Сохраняются Markdown-отчёт и HTML-копия.

## Завершение

Проход окончен, когда выбранный охват обработан, кандидаты разобраны, ограничения перечислены, отчёт сохранён. Найденные дефекты не останавливают проход.

Частичное покрытие допустимо только при конкретном препятствии (нет кода зависимости, запуск запрещён, инструмент недоступен), остановке пользователем или явном ограничении объёма. Для каждого остатка указывается, что не проверено, какое препятствие и что нужно для продолжения. «Не все ветви прослежены» — это незавершённая работа, а не ограничение.

## Контракт проверки

Каждая проверка (`TOOL-CHK-N`, `REL-CHK-N`, `SEC-CHK-N`) описывается полями:

```text
Предмет
Когда применима
Основание
Способ
Условие прохождения
Отсутствие доказательств
```

Основание находки — одно из:

- правило языка или платформы;
- контракт API;
- техническое соглашение, зафиксированное в репозитории;
- техническая гарантия, установленная кодом проекта: в коде есть потребитель, который полагается на результат производителя (читает хранилище как согласованное с другим, ищет выведенную сервером разметку, повторяет запуск до изменения условия), либо механизм сам объявляет результат (синхронизация, восстановление, «одна оценка на пользователя»).

Желаемое поведение, на которое в коде не опирается ни один потребитель, основанием не является.

Общие принципы:

- **Достижимость.** Отсутствие вызова или шаблона само по себе не дефект. Дефект — достижимый путь к последствию: fatal error, потеря или порча данных, неверный результат для вызывающего кода, раскрытие данных, обход ограничения.
- **Перечни — примеры.** Списки функций в «Когда применима» помогают узнать класс, но не ограничивают проверку. Критерий задаётся контрактом.
- **Сверка с исходником.** Решающее утверждение о поведении ядра, плагина или библиотеки сверяется с локальным исходником зависимости; в доказательстве — файл и строка. Без исходника — документация с пометкой, а решающий непроверенный вывод остаётся гипотезой.
- **Инвариант для повторов.** Повтор и частичный отказ оцениваются только при обоснованном инварианте. Универсальные требования идемпотентности и атомарности не приписываются.
- **Модель доступа не придумывается.** Несогласованность проверок прав — находка, если показан путь обхода конкретного ограничения. Если ожидаемые ограничения установить нельзя, это ограничение проверки, а не дефект.

## tooling

Используются существующие команды проекта: `scripts` в `composer.json` и `package.json`, `Makefile`, CI, конфигурации инструментов.

Запускаются только диагностические команды. Не запускаются:

- автоисправление;
- миграции и импорт;
- сборка, перезаписывающая отслеживаемые файлы;
- установка зависимостей без разрешения;
- тесты с доступом к живой БД, внешним сервисам или сайту;
- WP-CLI против сайта.

Из внешних обращений допустимы чтение результатов CI и аудит зависимостей. Кэши инструментов допустимы, по возможности вне репозитория.

Проверки области:

| ID | Предмет |
|---|---|
| TOOL-CHK-1 | Обязательные проверки проекта: результаты и разбор сообщений |
| TOOL-CHK-2 | Покрытие CI: обязательные проверки, которых в CI нет |
| TOOL-CHK-3 | Совместимость с заявленными версиями PHP и WordPress |
| TOOL-CHK-4 | Состояние зависимостей: уязвимости, согласованность lock-файлов |

На `scope: diff` инструменты запускаются по изменённым файлам, если это поддерживается, иначе — в штатном охвате. Результат — диагностика текущего состояния: наличие ошибки в изменённом файле не доказывает, что её внёс diff.

Находкой становится только разобранное сообщение. Неразобранные остаются в сводке без важности.

## security

**Реестр точек входа** (`E-N`) строится поиском по типам:

- AJAX и `admin-post`;
- REST;
- обработчики на ранних хуках;
- страницы администрирования и Settings API;
- шорткоды и блоки;
- шаблоны фронтенда;
- данные в REST ядра (`show_in_rest`, `register_meta`);
- изменение модели прав;
- загрузка файлов;
- собственные URL;
- XML-RPC и Heartbeat;
- cron;
- WP-CLI;
- прямой доступ к файлам.

Реестр задаёт знаменатель «проверено N из M». Точка проверена, когда путь от неё прослежен до значимых операций.

Проверки по типам используют общие вопросы: кто может вызвать, проверка прав и nonce, владение объектом, санитизация, экранирование по контексту.

Сквозные проверки не привязаны к одному типу точки входа:

| ID | Предмет |
|---|---|
| SEC-CHK-1 | Потоки данных: ввод → хранение → вывод, контексты экранирования, секреты |
| SEC-CHK-2 | Неявные и локальные защиты данных: пароль записи, статус и `read_post`, kses и `unfiltered_html`, фильтры `the_content`, видимость в REST ядра, meta caps |

## reliability

| ID | Предмет |
|---|---|
| REL-CHK-1 | Результат, который может быть `WP_Error` |
| REL-CHK-2 | Отказ, сообщаемый возвращаемым значением (`false`, `null`, `0`), при чтении и записи |
| REL-CHK-3 | Ответы внешних HTTP-запросов |
| REL-CHK-4 | Некорректный и отсутствующий ввод |
| REL-CHK-5 | Контракт REST-ответа и хуков |
| REL-CHK-6 | Порядок загрузки и доступность API |
| REL-CHK-7 | Ресурсы и состояние |
| REL-CHK-8 | Повторы и частичные отказы |
| REL-CHK-9 | Работа с БД |
| REL-CHK-10 | Соглашения проекта об обработке ошибок |
| REL-CHK-11 | Механизмы с состоянием на стыках компонентов |
| REL-CHK-12 | Завершение повторных запусков |

REL-CHK-11 и REL-CHK-12 идут не от отдельного вызова, а от механизма целиком: состояние производится, хранится и потребляется в разных компонентах, хранилищах или средах. Состояния выводятся из ветвлений кода и контрактов API. Статус «пройдена» без перечня рассмотренных состояний не ставится.

Точка входа, безопасная по `security` (CLI-скрипт, импорт, обработчик только для администратора), проходит `reliability` наравне с остальными.

## Отчёт

Сохраняется в `docs/reviews/wp-project-review-YYYY-MM-DD-HHMMSS.md` проверяемого проекта. Явно указанный путь имеет приоритет. Существующие файлы не перезаписываются. Отчёт на русском; параметры, уровни, ID, код и вывод инструментов не переводятся.

Структура: параметры проверки, итог, находки, покрытие, ограничения и открытые вопросы, рекомендации. Классификации, шаблон находки и самопроверка — в `reporting.md`; описание для пользователя — в [руководстве](../userguides/report.md).

Вердикта о готовности к релизу и P0/P1/P2 нет.

### HTML-копия

После сохранения Markdown запускается `scripts/report-html.py` — единственная команда вне `tooling`. Скрипт опирается на разметку из `reporting.md`:

- `## N. Раздел` — разделы и оглавление;
- в разделе «Находки» подзаголовки `###` — группы, `#### ID. Суть` — карточки;
- строка `**Область / тип / важность:** область · тип · уровень` — бейджи и фильтры;
- `- E-N · …`, `| E-N |`, `- **REC-N.** …` — цели ссылок;
- раздел «Покрытие» сворачивается по подзаголовкам `###`.

При изменении шаблона отчёта скрипт проверяется: число карточек должно совпасть с числом находок, ссылки на ID — вести на существующие элементы.

Скрипт экранирует весь текст: в отчётах встречается полезная нагрузка из находок вроде `<img src=x onerror=…>`, и в HTML она должна остаться текстом.
