# Как вносить изменения

## Разработка

Подключите рабочую копию как скилл симлинком, чтобы агент сразу видел правки:

```bash
git clone https://github.com/yarops/wp-project-check.git ~/projects/wp-project-check
ln -s ~/projects/wp-project-check ~/.claude/skills/wp-project-review
```

В Windows вместо симлинка — junction (симлинк требует Developer Mode):

```powershell
cmd /c mklink /J "$HOME\.claude\skills\wp-project-review" "$HOME\projects\wp-project-check"
```

Прогон использует то состояние, которое выгружено в рабочее дерево. Перед прогоном, по которому вы оцениваете версию, закоммитьте правки и проверьте, что дерево чистое: иначе результат нельзя привязать к версии.

## Почему методику легко испортить

Самый естественный ход — добавить правило под каждый пропуск. Он ведёт в тупик:

- **Подгонка.** Скилл учится находить известные дефекты конкретного кейса.
- **Неполные перечни.** Ревьюер читает список функций в правиле как исчерпывающий и пропускает всё, чего в нём нет.
- **Рост стоимости.** Файлы скилла читаются в каждом прогоне и остаются в контексте на каждом шаге. Лишний килобайт оплачивается многократно, а каждое новое правило размывает внимание к остальным.
- **Шум вместо сигнала.** Разброс между прогонами одной версии сопоставим с эффектом отдельной правки. Вывод по одному прогону легко оказывается выводом по шуму.

## Правила изменения методики

- **Порог.** Методика меняется, если пропуск повторяется не менее чем в двух прогонах одной версии или проявляется больше чем на одном проекте. Единичный пропуск записывается в результаты, но правку не вызывает.
- **Сначала существующее правило.** Найдите проверку, которая должна была сработать, и установите, почему не сработала: перечень прочитан как исчерпывающий, статус «пройдена» поставлен без проверенных мест, проверка не применена к месту. Правьте её формулировку. Новая проверка — только если класс дефекта не покрывает ни одна существующая.
- **Обобщение вместо перечня.** Перечни функций — примеры, критерий задаётся контрактом. Новые имена добавляются, только если без них класс не узнаётся.
- **Бюджет размера.** Правка не увеличивает суммарный объём `SKILL.md` и `references/`. Добавленное компенсируется сжатием, в первую очередь дублей между файлами.
- **Без ответа в примерах.** Пример метода в проверке не описывает дефект из регрессионного кейса. Иначе результат на кейсе показывает, что агент следует подсказке, а не что метод работает.
- **Исключение — достоверность покрытия.** Правка, без которой отчёт может заявлять охват, которого не было (молча пропущенные файлы, «пройдена» без проверенных мест), вносится по первому случаю.

Пример того, как правила работают. Ревьюер пропустил отказ записи меты, выданный клиенту за успех, и поставил «пройдена» проверке контрактов возврата: в её перечне были только функции чтения. Вместо новой проверки «результат записи» с ещё одним списком функций существующая проверка обобщена: перечень объявлен примерами, критерий — «отказ, сообщаемый возвращаемым значением», вопрос — что получат вызывающий код и следующий шаг при отказе.

## Регрессионный прогон

Версии сравниваются на проекте с известными дефектами. Обезличенное описание текущего кейса и результаты — в [docs/examples/demo-arcade](../examples/demo-arcade/).

Условия, одинаковые для всех прогонов:

- новая сессия без контекста прошлых прогонов и без доступа к таблице ожидаемых дефектов;
- прошлые отчёты убраны из проверяемого проекта;
- скилл на закоммиченной версии, дерево чистое;
- снимок проекта сверен по HEAD и хэшам lock-файлов; при расхождении — новый снимок без сравнения с прошлыми прогонами;
- одинаковый запрос, например `scope: global, areas: tooling, reliability, security`.

Headless-прогон с журналом событий:

```bash
cd <проект>
claude -p "/wp-project-review scope: global, areas: tooling, reliability, security" \
  --model <модель> --permission-mode auto \
  --output-format stream-json --verbose > run.jsonl
```

Метрики:

| Метрика | Как считать |
|---|---|
| Пропуски | ожидаемые дефекты без находки; совпадение — по причине и пути, а не по формулировке и важности |
| Ложные срабатывания | находки, отклонённые независимой сверкой |
| Доказательства | у находки есть путь, основание, условие; для фактов о платформе — файл и строка исходника |
| Покрытие | все ли файлы перечня прочитаны или указаны в ограничениях |
| Расход | из события `type: result`: `total_cost_usd`, `usage` (input, cache write и read, output, thinking), `num_turns`, `duration_ms`; пик контекста — максимум `input + cache_creation + cache_read` по сообщениям ассистента |

Находки вне таблицы ожидаемых сверяются отдельно. Подтверждённые пополняют таблицу, отклонённые считаются ложными срабатываниями.

## Чеклист правки

- Определено, какое существующее правило не сработало и почему.
- Объём `SKILL.md` + `references/` не вырос (`wc -c SKILL.md references/*.md`; PowerShell: `(Get-ChildItem SKILL.md, references\*.md | Measure-Object Length -Sum).Sum`).
- В примерах нет дефектов регрессионного кейса.
- Если менялся шаблон отчёта в `reporting.md`, `scripts/report-html.py` проверен на отчёте нового формата. Скрипт должен работать на Python 3.8.
- Если меняется поведение скилла, обновлены [контракт](contract.md) и руководства пользователя.
- Сообщение коммита: `feat:` / `fix:` / `docs:` и глагол в третьем лице, например `fix: Обобщает REL-CHK-2 на отказ записи`.
