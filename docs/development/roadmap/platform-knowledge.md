# Знания о платформе

Статус: отложено.

## Идея

Отделить метод (вопросы, условия, доказательство, покрытие) от фактов о платформе. Факты переносятся в небольшие файлы базы знаний с индексом триггеров «встретил X → прочитай Y». Вопрос остаётся в методе со ссылкой на файл базы, иначе агент её не откроет.

```text
references/
├── reliability.md, security.md, …   # метод
└── kb/
    ├── index.md                      # триггеры
    ├── implicit-protections.md
    ├── wpdb.md
    ├── core-rest-exposure.md
    ├── browser-storage.md
    └── …
```

Правила:

- Файл — одна тема, 1–3 КБ.
- Факт — это утверждение и источник для сверки: функция WordPress, контракт PHP, спецификация browser API или исходник конкретной реализации.
- Ограничения, зависящие от браузера (лимиты cookie и `localStorage`, приватный режим), помечаются как зависящие от браузера. В находке они — условие достижимости, а основанием служит контракт API («запись может не выполниться»).
- Индекс загружается вместе с методом области, файлы базы — только по триггеру.

## Почему отложено

Факт стоит выносить, только если он нужен лишь при определённом механизме и при этом занимает заметный объём. Сейчас под этот критерий попадает около 7 КБ из ~130 КБ методики, а индекс добавит около 1 КБ, который читается всегда. Экономия в несколько процентов ниже разброса между прогонами, поэтому эффект нельзя измерить.

## Внешние источники

Рассмотрены как возможный источник фактов:

| Источник | Польза |
|---|---|
| [WordPress/agent-skills](https://github.com/WordPress/agent-skills) | Скиллы для разработки: блоки, REST, производительность, cron. Полезны точечные факты; базовые правила безопасности там слабее, чем в `security.md`. Формат eval-сценариев — образец для проверочных проектов. Целиком не подключать; факты пересказывать со ссылкой (GPL-2.0). |
| Исходники ядра | Нужны для подтверждения выводов о поведении API. Клон не нужен: у проверяемого сайта обычно есть локальный `wp-includes/` нужной версии. Это уже правило методики. |
| [WordPress Coding Standards](https://github.com/WordPress/WordPress-Coding-Standards) | Сниффы проверяют шаблоны, а не достижимость: в `tooling` это сигналы, а не находки. Тестовые файлы сниффов — источник примеров для проверочных проектов. |
| [wordpress-stubs](https://github.com/php-stubs/wordpress-stubs), [phpstan-wordpress](https://github.com/szepeviktor/phpstan-wordpress) | Типы возврата API ядра. Если пакет установлен в проекте, при чтении кода — локальный справочник типов. |
| [plugin-check](https://github.com/WordPress/plugin-check) | Требования каталога WP.org; отложено до [профилей поставки](plugin-theme-profiles.md). |

Ни один источник не содержит того, чего ревьюеру не хватало на практике: перечня защит, которые платформа применяет неявно, и мест, где код их обходит (пароль записи только в `get_the_content()`, повторное декодирование после kses, видимость данных в REST ядра, meta caps). Такой перечень написан самостоятельно и вошёл в сквозную проверку `SEC-CHK-2`.

## Условия возврата

- references выросли примерно на 20 КБ фактов либо появилась область фактов, нужная лишь части проектов;
- или точечные факты из внешних источников набирают заметный объём.

При возврате нужно заново разметить references и переносить факты отдельным этапом с прогоном после него.
