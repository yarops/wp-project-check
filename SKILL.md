# wp-project-review

Проверка технической корректности кодовой базы WordPress-проекта и соблюдения формальных требований языка, платформы, API и технических соглашений, зафиксированных в репозитории. Бизнес-логика, полнота фич и соответствие продуктовой задаче в охват не входят; задача или критерии приёмки фичи не являются обязательным входом.

Скилл выполняет только ревью и выдаёт отчёт. Исходники и конфигурацию проекта не изменяет, дефекты не исправляет.

## Язык

С пользователем — только на русском: уточняющие вопросы, уведомления, промежуточные сообщения, отчёт. Язык запроса на это не влияет.

Без перевода: имена параметров и их значения (`scope`, `diff`, `areas`, `security`…), уровни Critical / High / Medium / Low, ID находок, код, пути, функции, хуки, capabilities, команды и вывод инструментов. Термины WordPress (хук, nonce, capability, REST-маршрут) — в принятой форме.

## Поддерживаемые области

| Область | Статус в текущей версии | Reference |
|---|---|---|
| `tooling` | реализована | `references/tooling.md` |
| `reliability` | реализована | `references/reliability.md` |
| `security` | реализована | `references/security.md` |
| `architecture` | **не реализована** | — |
| `operations` | **не реализована** | — |

Реализованы только области, у которых есть reference в этой таблице. Описание области в контракте или планах не означает её реализацию.

Правила для нереализованных областей:

- Явно запрошена нереализованная область — сообщить, что она пока не поддерживается. Не выполнять её и не подменять произвольным ревью или другой областью.
- Запрошены реализованные и нереализованные — сообщить об ограничении, выполнить только реализованные. В отчёте перечислить невыполненные области с причиной «не реализована в текущей версии скилла».
- Все запрошенные области не реализованы — завершить работу уведомлением об отсутствии поддержки. Отчёт и вердикт о качестве проекта не выдаются.
- Запуск без `areas` — до начала работы сообщить: выполняются `tooling`, `reliability`, `security`; `architecture` и `operations` пока не реализованы. Полнота отчёта ограничена реализованными областями.

Типовые формулировки запроса, относящиеся к нереализованным областям: границы модулей, слои, зависимости между компонентами, соблюдение архитектурных соглашений (`architecture`); миграции на стенде, конфигурация окружения, восстановление, откат, деплой (`operations`). Если запрос сводится к ним, применяются правила выше.

Проверки требований каталогов публикации (включая WP.org) и специализированные профили плагинов и тем в текущую версию не входят.

## Параметры запуска

| Параметр | Значения | По умолчанию |
|---|---|---|
| `scope` | объект с `type`: `diff` / `feature` / `global` | `{type: global}` |
| `areas` | `tooling`, `reliability`, `security` (`architecture`, `operations` — не реализованы) | все реализованные |
| `target` | `plugin` / `theme` / `site` | определяется по кодовой базе |

`scope`:

- `type: diff`, поле `base` обязательно (ветка, тег или коммит) — изменения относительно `base` и их влияние на существующее поведение. Связанный код читается по необходимости. Фиксируется проверяемое состояние: HEAD и наличие незакоммиченных изменений в охвате.
- `type: feature`, поле `subject` обязательно — код функции или сценария со связанным путём выполнения, даже если он распределён по файлам и хукам. Это выбор охвата кода, а не проверка продуктового смысла.
- `type: global` — весь проверяемый проект, без дополнительных полей.

Предыдущий отчёт не является базой сравнения кода. Повторная проверка закрытия прошлых находок не поддерживается.

YAML не обязателен: запрос на естественном языке преобразуется в те же параметры. Уточнять только существенные неоднозначности (например, нет `base` для diff и его нельзя вывести из запроса). Явно указанные `scope` и `areas` ограничивают проверку.

Параметра окружения нет. Сценарии, запросы к endpoint и WP-CLI на работающем сайте не выполняются, в том числе для подтверждения находки. Находка, которую нельзя подтвердить без такого запуска, остаётся гипотезой.

## Порядок работы

### 1. Собрать контекст

Прочитать `references/project-context.md`. Определить `target` и его признаки, границы собственного кода, технические правила и соглашения репозитория, доступные доказательства (CI, тесты, конфигурация инструментов), охват `scope`. Вопросы пользователю — только по существенным пробелам, которые нельзя закрыть чтением репозитория.

### 2. Зафиксировать план

Сверить запрошенные области с таблицей «Поддерживаемые области» и уведомить пользователя об ограничениях. Для каждой выполняемой области загрузить её reference и выбрать применимые проверки: для каждой — основание и способ проверки. Неприменимые проверки отметить с причиной.

План фиксируется до прохода. Расширение охвата допускается только из-за новой находки или обнаруженной зависимости, и причина расширения записывается.

### 3. Выполнить проходы

Рекомендуемый порядок: `tooling` (результаты инструментов дают сигналы для чтения кода) → `security` (реестр точек входа) → `reliability`. Вести учёт проверенного и оставшегося. Reference каждой области загружается только при её запуске.

Команды запускаются только в рамках `tooling` и только диагностические — правила в `references/tooling.md`. В `reliability` и `security` команды проекта не запускаются, проверка ведётся чтением кода.

### 4. Разобрать кандидатов в находки

Исключить дубликаты (одна причина — одна находка, даже если её видно из нескольких областей). Для каждого кандидата проверить предпосылки, достижимость и последствия. Определить тип замечания и важность, приложить доказательство нужного вида — правила в `references/reporting.md`. Без доказательства нужного вида кандидат остаётся гипотезой; без установленного дефекта — недостатком технического контекста или рекомендацией.

### 5. Выдать отчёт

Перед выдачей сверить фактическое покрытие с планом и правилами завершения ниже. Если осталась доступная работа в выбранном охвате, продолжить проход. Затем прочитать `references/reporting.md` и сохранить полный отчёт в Markdown-файл. По умолчанию — `docs/reviews/wp-project-review-YYYY-MM-DD-HHMMSS.md` относительно корня проверяемого проекта; явно указанный пользователем путь имеет приоритет. Правила сохранения и краткого ответа — в reference. Вердикта о готовности к релизу нет.

## Общие правила проверки

Каждая проверка описывается полями: предмет; когда применима; основание (правило языка или платформы / контракт API / техническое соглашение из репозитория); необходимый контекст и доступ; способ проверки; условие прохождения; что означает отсутствие доказательств.

- Отсутствие определённого вызова или шаблона кода само по себе не дефект. Дефект — нарушение основания на достижимом пути выполнения.
- Основание — только правила языка, платформы, контракты API и соглашения, зафиксированные в репозитории. Собственные вкусовые предпочтения и продуктовые требования основанием не являются.
- Чего нельзя установить из кода и документации — фиксируется как ограничение, а не додумывается.

Статусы проверки: пройдена; обнаружено нарушение; неприменима — с причиной; не проверена — с причиной; выполнена частично — с границами.

Завершённость прохода и результат проверки различаются. Если проверка выявила хотя бы один подтверждённый дефект, её статус — «обнаружено нарушение», даже если все кандидаты разобраны. «Пройдена» — только когда нарушений нет.

## Запреты

- Не изменять исходники, конфигурацию и данные проекта; не исправлять дефекты; не предлагать готовые патчи в отчёте (только направление исправления).
- Не создавать и не изменять файлы в репозитории, кроме Markdown-отчёта и необходимого для него каталога, а также кэшей и временных файлов инструментов (по возможности — вне репозитория).
- Не устанавливать зависимости без явного разрешения пользователя.
- Не обращаться к работающему сайту, живой БД и внешним сервисам. Исключение — диагностические обращения в рамках `tooling`: чтение результатов CI и запросы аудита зависимостей к базам уязвимостей (`references/tooling.md`, п. 2а).
- Не выполнять нереализованные области и не подменять их.

## Завершение

Проход окончен, когда выбранный охват обработан, кандидаты разобраны, ограничения перечислены, отчёт сохранён и пользователю сообщён его путь. Готовность к релизу оценивается отдельно, по заранее определённым обязательным условиям проекта, и из отчёта не выводится.

Найденные дефекты не являются основанием для остановки: продолжать проверку оставшегося охвата, включая ещё не разобранные пути выполнения и поиск точек входа. Для `global` выборка основных обработчиков не заменяет проход по всему собственному коду в выбранных областях.

Различать незавершённую работу и недоступную проверку. «Не все ветви прослежены» или «реестр не завершён» описывают оставшуюся работу: её нужно выполнить, если нет конкретного препятствия. Статусы «не проверена» и «выполнена частично» сами по себе не разрешают завершить проход.

Завершение с частичным покрытием допустимо, если оставшаяся проверка упирается в конкретное препятствие (например, отсутствующий код зависимости, недоступный инструмент или запрещённый запуск), пользователь остановил работу либо явно ограничил её объём или время. Для каждого остатка указать, что именно не проверено, препятствие и что требуется для продолжения. Ограничение одного пути не останавливает доступную работу в остальных частях охвата. При вынужденной остановке до выполнения этих условий результат обозначается как промежуточный, с перечнем оставшейся работы.
