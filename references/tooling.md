# Область tooling

Предмет: команды проекта, результаты CI, линтинг, статический анализ, состояние зависимостей, тесты в изолированном окружении.
Результат: результаты инструментов и ограничения их покрытия.

Используются существующие команды и настройки проекта. Скилл не добавляет инструменты, конфигурацию и пайплайны: если обязательной проверки нет в CI, это отмечается отдельно, а добавление пайплайна — самостоятельная задача.

## 1. Инвентаризация

Собрать список проверок проекта из `composer.json` (`scripts`), `package.json` (`scripts`), `Makefile`, CI-конфигурации и конфигов инструментов (см. `project-context.md`, п. 4).

Для каждого инструмента зафиксировать:

- команду в том виде, в каком её запускает проект или CI;
- конфигурацию и baseline;
- запускается ли она в CI;
- категорию безопасности (см. п. 2).

Типовые инструменты WordPress-проекта: PHPCS с WPCS/PHPCompatibility, PHPStan (часто с `szepeviktor/phpstan-wordpress`), Psalm, `php -l`, PHPUnit, `composer validate`, `composer audit`, ESLint/Stylelint (`wp-scripts lint-js`, `lint-style`), `npm audit`, Jest (`wp-scripts test-unit-js`).

## 2. Допустимые команды

Запускаются только диагностические команды: линтеры, статический анализ, проверка зависимостей, тесты. Команда не должна изменять исходники, конфигурацию проекта и данные работающего сайта.

Не запускаются:

- автоисправление: `phpcbf`, `eslint --fix`, `stylelint --fix`, `prettier --write`, `wp-scripts format`, `composer normalize` без `--dry-run`, `rector process` без `--dry-run` и аналоги;
- миграции, установка и обновление схемы, импорт данных;
- сборка или генерация, перезаписывающая отслеживаемые файлы (`npm run build`, `wp-scripts build`, `wp i18n make-pot` в отслеживаемый файл и т. п.);
- установка и обновление зависимостей: `composer install/update`, `npm install/ci` (только с явного разрешения пользователя, см. п. 4);
- тесты и скрипты, подключающиеся к живой БД, внешним сервисам или работающему сайту (диагностические обращения из п. 2а к ним не относятся);
- WP-CLI против любого сайта.

Перед запуском скрипта проекта прочитать, что он делает на самом деле: имя `lint` или `test` не гарантирует безопасность (скрипт может вызывать `--fix`, сборку или цепочку других скриптов).

Тесты допустимы, если используют изолированное тестовое окружение проекта: unit-тесты без WordPress (Brain Monkey, WP_Mock), Jest, интеграционные тесты с отдельной тестовой БД, которая создаётся и очищается тестовым окружением. Признаки опасности: в `phpunit.xml`/`wp-tests-config.php` указаны боевые реквизиты БД, тесты обращаются к внешним URL, требуется запущенный сайт.

Если по команде и конфигурации нельзя установить, что она безопасна, команда не запускается, проверка получает статус «не проверена» с причиной.

Кэши и временные файлы инструментов (`.phpunit.result.cache`, кэши PHPCS и PHPStan, `.eslintcache`) допустимы. Если инструмент позволяет, размещать их вне репозитория, например:

- PHPCS: `--cache=<tmp>/phpcs.cache` или `--no-cache`;
- PHPStan: `tmpDir` задаётся в конфиге — если конфиг проекта указывает каталог в репозитории, это допустимо;
- PHPUnit: `--cache-result-file=<tmp>/.phpunit.result.cache` (или `--do-not-cache-result`).

### 2а. Допустимые диагностические обращения к внешним сервисам

Разрешены только чтение результатов CI (п. 3) и запросы инструментов аудита зависимостей к базам уязвимостей (`composer audit`, `npm audit` без `fix`). Они ничего не изменяют и не выполняют проверяемый код. Сценарии проекта, endpoint и интеграции против внешних систем по-прежнему не запускаются. Если сеть недоступна, проверка получает статус «не проверена» с причиной.

## 3. Результаты CI

Если доступны результаты последнего прогона CI (например, через `gh run list` / `gh run view` для текущего коммита или ветки), их можно использовать как доказательство с указанием коммита и даты прогона. Результат CI для другого коммита не подтверждает текущее состояние — это указывается. Отсутствие доступа к CI — ограничение, не дефект.

## 4. Недоступные инструменты

- Если команды проекта недоступны без установки зависимостей или иной подготовки окружения (нет `vendor/`, `node_modules/`, нет нужной версии PHP или Node, нужен Docker/`wp-env`), проверка получает статус «не проверена» с указанием причины и необходимого действия.
- Скилл не устанавливает зависимости самостоятельно. Можно один раз предложить пользователю установку; при явном разрешении установить и зафиксировать в отчёте, что окружение было подготовлено и какой командой.
- Глобально установленные инструменты вместо проектных не используются по умолчанию: их версия, стандарты и настройки могут расходиться с проектными. Допустимо только с согласия пользователя; в отчёте указываются версия глобального инструмента, использованная конфигурация проекта и возможное расхождение. Установка во временную копию репозитория в текущей версии не выполняется.

## 5. Tooling при `scope: diff`

- Запускать по изменённым файлам (из охвата, после фильтра по собственному коду и по типам файлов инструмента), если инструмент поддерживает такое ограничение: PHPCS, ESLint, Stylelint, `php -l` принимают список файлов; PHPStan принимает пути, но анализирует их с учётом всего проекта.
- Использовать команды и настройки проекта, включая baseline.
- Если инструмент требует анализа всего проекта или не поддерживает сужение (тесты, `composer audit`, Psalm с некоторыми конфигурациями) — штатный охват.
- В отчёте — фактический охват каждого запуска.

Результаты — диагностика текущего состояния. Наличие ошибки в изменённом файле или сверх baseline не доказывает, что она внесена текущим diff. Связь с изменением утверждается только при доказательстве (например, ошибка указывает на строку, добавленную в diff, и по смыслу вызвана изменением). Сравнение результатов на `base` и текущем состоянии не выполняется.

Обязательные ограничения в отчёте для `diff`: в результат могут попасть существовавшие ошибки; при запуске по изменённым файлам могут быть пропущены ошибки вне этих файлов, вызванные изменением.

## 6. Разбор результатов

- Сырой вывод в отчёт не переносится. По каждому инструменту — сводка: количество сообщений по правилам или категориям.
- Находкой (`TOOL-N`) с типом и важностью становится только сообщение, разобранное ревьюером: проверены контекст, достижимость и последствия по общим правилам `reporting.md`. Доказательство — разобранное сообщение с контекстом.
- Неразобранные сообщения остаются в сводке без важности и не считаются подтверждёнными дефектами.
- Приоритет разбора: ошибки (а не warnings), сообщения о безопасности (`WordPress.Security.*`, `WordPress.DB.PreparedSQL*`), совместимости с заявленными версиями PHP/WP (`PHPCompatibility`), ошибки типов PHPStan на путях из охвата, падающие тесты, уязвимости зависимостей.
- Если сообщение инструмента указывает на проблему, которая разбирается в `security` или `reliability`, — одна находка в соответствующей области со ссылкой на сообщение инструмента; дубликаты не создаются.
- Уязвимость зависимости (`composer audit`, `npm audit`) становится подтверждённым дефектом только при доказательстве, что уязвимый код достижим в проекте; иначе — гипотеза или запись в сводке. Dev-зависимость, не попадающая в поставку, — указывается.
- Падающий тест: разобрать причину; тест, падающий из-за окружения, а не кода, — ограничение, не дефект.

Чтение кода в `reliability` и `security` не заменяет результаты инструментов, а инструменты не заменяют чтение кода.

## 7. Проверки области

### TOOL-CHK-1. Обязательные проверки проекта

- Когда применима: в проекте есть настроенные линтеры, статанализ или тесты.
- Основание: конфигурация инструментов и CI в репозитории.
- Способ: запустить безопасные команды проекта (п. 2), разобрать результат.
- Условие прохождения: команда завершилась без ошибок в охвате либо каждая ошибка разобрана и признана ложным срабатыванием или неприменимой с обоснованием.
- Статус при ошибках: есть хотя бы один подтверждённый дефект — «обнаружено нарушение»; подтверждённых дефектов нет, но часть сообщений не разобрана — «выполнена частично» с указанием числа неразобранных сообщений. Завершённость разбора не делает проверку пройденной.
- Отсутствие доказательств: команда не запущена — «не проверена» с причиной.

### TOOL-CHK-2. Покрытие CI

- Когда применима: в репозитории есть настроенные инструменты.
- Основание: конфигурация инструментов и CI.
- Способ: сопоставить настроенные инструменты с шагами CI.
- Условие прохождения: настроенные проекты инструменты запускаются в CI.
- Отсутствие доказательств: CI-конфигурации нет или она недоступна — отметить отдельно; это рекомендация или ограничение, не дефект кода.

### TOOL-CHK-3. Совместимость с заявленными версиями

- Когда применима: заявлены `Requires PHP` / `Requires at least` или `config.platform.php`.
- Основание: заявленные требования и `testVersion` / `minimum_wp_version` проекта.
- Способ: сверить заявленные версии между заголовком, `readme.txt`, `composer.json` и конфигами инструментов; результаты PHPCompatibility, если настроен.
- Условие прохождения: значения согласованы, нарушений в охвате нет.
- Отсутствие доказательств: инструмента нет — сверка значений выполняется, проверка кода на совместимость получает статус «выполнена частично».

### TOOL-CHK-4. Состояние зависимостей

- Когда применима: есть `composer.json`/`composer.lock` или `package.json`/lock-файл.
- Основание: манифест и lock-файл, базы уязвимостей, используемые инструментами.
- Способ: `composer validate --no-check-publish` (только чтение), `composer audit --locked`, `npm audit` (без `fix`) — если доступны и не требуют установки; согласованность lock-файла с манифестом.
- Условие прохождения: манифест валиден, известных уязвимостей в поставляемых зависимостях нет либо каждая разобрана и признана неприменимой (уязвимый код недостижим, зависимость не попадает в поставку) с обоснованием.
- Статус при уязвимостях: подтверждённая достижимая уязвимость — «обнаружено нарушение»; неразобранные сообщения — «выполнена частично».
- Отсутствие доказательств: нет сети или инструмента — «не проверена» с причиной.

## 8. Сводка для отчёта

По каждому инструменту:

```text
Инструмент: PHPCS (WordPress, PHPCompatibilityWP)
Команда: vendor/bin/phpcs --no-cache <файлы>
В CI: да / нет / неизвестно
Фактический охват: N изменённых PHP-файлов / весь проект (штатный охват)
Результат: N ошибок, M предупреждений / завершилась успешно / не запущена — причина
По правилам: WordPress.Security.EscapeOutput — 4, ...
Разобрано в находки: TOOL-1, SEC-2
Ограничения покрытия: ...
```
