# Сбор контекста

Цель шага — установить, что именно проверяется, по каким правилам и какими доказательствами. Контекст берётся из репозитория; вопросы пользователю — только по существенным пробелам.

## 1. Объект проверки (`target`)

Если `target` не указан, определить по признакам:

| `target` | Признаки |
|---|---|
| `plugin` | PHP-файл в корне с заголовком `Plugin Name:` в docblock |
| `theme` | `style.css` в корне с заголовком `Theme Name:`; `Template:` — дочерняя тема; `theme.json` + `templates/` — блочная |
| `site` | `wp-config.php`; структура Bedrock (`web/app`, `config/application.php`); `wp-content` с собственным кодом проекта |

Способ поиска:

```bash
grep -l "Plugin Name:" *.php 2>/dev/null
grep -l "Theme Name:" style.css 2>/dev/null
ls wp-config.php web/app config/application.php wp-content 2>/dev/null
```

- Если `target` указан и противоречит признакам — сообщить о расхождении и уточнить.
- Если в репозитории несколько самостоятельных объектов (например, монорепозиторий с плагином и темой) и запрос не позволяет выбрать — уточнить предмет проверки.
- В отчёт: определённый `target` и признаки, по которым он определён (файл и заголовок).

## 2. Границы собственного кода (для `site` и смешанных репозиториев)

Проверяется собственный код: mu-plugins, собственные плагины и темы, конфигурация в репозитории. Ядро WordPress, сторонние плагины и темы — зависимости: их код не ревьюится, а их состояние входит в `tooling` в той мере, в какой его покрывают команды проекта.

Источники для разделения:

- инструкции и документация проекта (`README`, `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING`, `docs/`);
- `composer.json`: пакеты из `wpackagist`, `installer-paths` — сторонние; `path`-репозитории и собственный namespace — свои;
- `.gitignore`: игнорируемые каталоги плагинов и тем — как правило, сторонние;
- `vendor/`, `node_modules/` — всегда зависимости.

Если границу установить нельзя — уточнить у пользователя. В отчёт: какие каталоги признаны собственным кодом и на каком основании.

## 3. Технические правила и соглашения

Собрать то, что может служить основанием находок:

- требования к окружению: `Requires PHP`, `Requires at least`, `Tested up to` в заголовке плагина/темы или `readme.txt`; `require.php` и `config.platform.php` в `composer.json`;
- стандарты кода: `phpcs.xml(.dist)`, `.phpcs.xml.dist` (набор правил, `testVersion`, `minimum_wp_version`, `text_domain`, `prefixes`), `phpstan.neon(.dist)` (уровень, baseline), `psalm.xml`, `.editorconfig`, `.eslintrc*`, `.stylelintrc*`;
- явно зафиксированные соглашения в документации и инструкциях проекта (префиксы, обработка ошибок, модель прав, слои);
- зарегистрированные проектом capabilities и роли (`add_role`, `add_cap`, `map_meta_cap`) — для `security`.

Соглашение считается основанием, только если оно зафиксировано в репозитории. Устные или предполагаемые соглашения — нет.

## 4. Доступные доказательства

- CI: `.github/workflows/`, `.gitlab-ci.yml`, `bitbucket-pipelines.yml`, `Jenkinsfile` и т. п. — какие проверки обязательны, какие команды запускаются.
- Команды проекта: `scripts` в `composer.json` и `package.json`, `Makefile`, `Taskfile`, `bin/`.
- Тесты: `phpunit.xml(.dist)`, `tests/`, `bin/install-wp-tests.sh`, `.wp-env.json`, e2e-конфигурация — и с каким окружением они работают.
- Наличие установленных зависимостей: `vendor/`, `node_modules/`.

## 5. Охват `scope`

### `diff`

```bash
git rev-parse --verify <base>
git rev-parse HEAD
git merge-base <base> HEAD
git diff --name-status <merge-base>...HEAD
git status --porcelain
```

- Сравнение — от merge-base с `base` до текущего состояния. Если незакоммиченные изменения в охвате есть, они включаются в проверку и это указывается в отчёте (`git diff` / `git diff --cached`).
- Если `base` не существует или репозиторий не git — уточнить; без базы `diff` не выполняется.
- Список изменённых файлов фильтруется по границам собственного кода.
- Связанный код (вызывающие, вызываемые, хуки, на которые подписан изменённый код) читается по необходимости, чтобы оценить влияние изменения.

### `feature`

- По `subject` найти точки входа и регистрации: хуки, маршруты, action, шорткоды, блоки, CLI-команды, строки интерфейса, имена классов и функций.
- Пройти путь выполнения от точек входа до значимых операций, включая код в других файлах и хуках.
- Если `subject` нельзя однозначно сопоставить с кодом — показать найденных кандидатов и уточнить.
- В отчёт: перечень файлов и точек входа, вошедших в охват, и как они найдены.

### `global`

Весь собственный код объекта проверки.

## 6. Что уточнять у пользователя

Только существенные пробелы, ответ на которые меняет охват или выводы:

- неоднозначный объект проверки или граница собственного кода;
- отсутствует или не существует `base` для `diff`;
- `subject` не сопоставляется с кодом;
- установка зависимостей для запуска инструментов (см. `tooling.md`).

Остальные пробелы фиксируются в отчёте как ограничения или недостаток технического контекста.

## Результат шага

Короткая сводка для плана и раздела «Параметры проверки» отчёта: `target` и признаки; границы собственного кода; охват и, для `diff`, проверяемое состояние; найденные основания (стандарты, требования к версиям, соглашения); доступные доказательства; открытые пробелы.
