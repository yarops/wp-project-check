# Область security

Предмет: точки входа, права, владение объектами, потоки данных.
Результат: находки и реестр проверенного охвата.

Проверка ведётся чтением кода. Запросы к работающему сайту для подтверждения не выполняются: если находку нельзя подтвердить кодом, она остаётся гипотезой.

## Основания

- правила платформы WordPress (модель capabilities, nonce, экранирование и санитизация, `$wpdb->prepare`, REST `permission_callback`);
- зарегистрированные проектом capabilities и роли, `permission_callback`, проверки в обработчиках;
- техническая документация репозитория о модели доступа.

Несогласованность проверок доступа может быть находкой, если показан достижимый путь обхода конкретного ограничения (например, AJAX-обработчик изменяет то же, что REST-маршрут, но без проверки capability, которую проверяет маршрут). Согласованность кода сама по себе не доказывает правильность модели доступа. Если ожидаемые ограничения установить нельзя — фиксируется ограничение проверки; продуктовая политика доступа не придумывается.

Если требуемые права уже легитимно дают тот же результат, находка снимается (например, «XSS» в настройке, доступной только с `unfiltered_html`; выполнение PHP администратором, который может редактировать плагины, — с учётом `DISALLOW_FILE_EDIT`/`DISALLOW_UNFILTERED_HTML`, если они зафиксированы в проекте).

## 1. Реестр точек входа

Проход начинается с реестра: перечня мест, через которые внешний ввод или действие пользователя попадает в код проекта. Реестр составляется при первичной инвентаризации охвата и уточняется по ходу анализа. Итоговый реестр — знаменатель покрытия M.

### Поиск

Статический поиск регистраций в охвате собственного кода (`vendor/`, `node_modules/` и сторонний код исключаются):

```bash
grep -rnE "wp_ajax_(nopriv_)?|admin_post_(nopriv_)?" --include=*.php <охват>
grep -rnE "register_rest_route|rest_api_init" --include=*.php <охват>
grep -rnE "\\\$_(GET|POST|REQUEST|COOKIE|FILES|SERVER)\b" --include=*.php <охват>
grep -rnE "add_(menu|submenu|options|management|theme)_page|register_setting|add_settings_field" --include=*.php <охват>
grep -rnE "add_shortcode|register_block_type|render_callback" --include=*.php <охват>
grep -rln "\"render\"" --include=block.json <охват>
grep -rnE "show_in_rest|register_meta|register_post_meta|register_term_meta|auth_callback" --include=*.php <охват>
grep -rnE "map_meta_cap|user_has_cap|'authenticate'|determine_current_user|add_role|add_cap" --include=*.php <охват>
grep -rnE "wp_handle_upload|wp_handle_sideload|media_handle_(upload|sideload)|upload_mimes|wp_check_filetype" --include=*.php <охват>
grep -rnE "add_rewrite_rule|add_rewrite_endpoint|query_vars" --include=*.php <охват>
grep -rnE "xmlrpc_methods|heartbeat_received|heartbeat_nopriv_received" --include=*.php <охват>
grep -rnE "wp_schedule_(single_)?event|as_schedule_|as_enqueue_async_action" --include=*.php <охват>
grep -rnE "WP_CLI::add_command" --include=*.php <охват>
```

Прямой доступ к файлам: PHP-файлы охвата без проверки `defined( 'ABSPATH' )` (или эквивалента) в начале, которые при прямом запросе выполняют что-то кроме объявления классов и функций.

Способ поиска (какие шаблоны и в каких каталогах) указывается в отчёте.

### Типы точек входа

| Тип | Как находится | Ключевые вопросы |
|---|---|---|
| AJAX | `wp_ajax_{action}`, `wp_ajax_nopriv_{action}` | Права, nonce, доступность без входа |
| REST | `register_rest_route` | `permission_callback`, валидация `args`, владение объектом |
| admin-post | `admin_post_{action}`, `admin_post_nopriv_{action}` | Права, nonce, перенаправление |
| Обработчики запросов на ранних хуках | Чтение `$_GET`, `$_POST`, `$_REQUEST`, `$_COOKIE` в обработчиках `init`, `wp_loaded`, `admin_init`, `template_redirect`, `parse_request` | Кто может вызвать: `admin_init` срабатывает и для неавторизованных запросов к `admin-ajax.php` и `admin-post.php` |
| Страницы администрирования | Обработка отправки в callback `add_menu_page` / `add_submenu_page`, `register_setting` | Права на действие, а не только на показ страницы; nonce; `sanitize_callback` |
| Шаблоны фронтенда (основной запрос) | Иерархия шаблонов темы, фильтр `template_include`, вызываемые части шаблонов и компоненты | Какие данные запрошенного объекта выводятся и применяется ли на этом пути защита ядра (пароль, статус); экранирование данных пользователей с меньшими правами; собственные запросы в шаблоне |
| Шорткоды | `add_shortcode` | Атрибуты от авторов с низкими правами, экранирование вывода |
| Блоки | `render_callback`, `render` в `block.json` | Атрибуты блока, экранирование вывода |
| Данные в REST ядра | `show_in_rest` у `register_post_type`, `register_taxonomy`, `register_meta`; `auth_callback` у meta | Какие данные и кому открываются через маршруты ядра |
| Изменение модели прав | `map_meta_cap`, `user_has_cap`, `authenticate`, `determine_current_user` | Не расширяют ли фильтры права или аутентификацию сверх задуманного |
| Загрузка файлов | `$_FILES`, `wp_handle_upload`, `media_handle_sideload`, фильтр `upload_mimes` | Тип и содержимое файла, путь сохранения, права |
| Собственные URL | `add_rewrite_rule`, `add_rewrite_endpoint`, фильтр `query_vars` | Обработчик и его проверки |
| XML-RPC и Heartbeat | Фильтры `xmlrpc_methods`, `heartbeat_received` | Права и возвращаемые данные |
| Cron | Обработчики хуков из `wp_schedule_event` / `wp_schedule_single_event` | Источник аргументов, повторный запуск |
| WP-CLI | `WP_CLI::add_command` | Обработка аргументов; последствия ошибочного вызова, например массовое изменение или удаление данных без подтверждения |
| Прямой доступ к файлам | PHP-файлы, исполняемые при прямом запросе без проверки `ABSPATH` | Что выполняется вне загрузки WordPress |

Перечень открыт: точка входа, не подходящая ни под один тип, вносится как «прочее» с описанием.

### Запись реестра

```text
ID: E-1, E-2…
Тип и идентификатор: action, маршрут, шорткод, хук
Регистрация: файл:строка
Обработчик: функция или метод
Кому доступна: без входа / любой авторизованный / capability
Статус: пройдена / обнаружено нарушение / неприменима / не проверена / выполнена частично
Находки: ID связанных находок
```

### Когда точка входа проверена

Точка входа проверена, когда для пути от неё до всех значимых операций разобраны все применимые к её типу вопросы. Значимые операции — те, где ввод или права влияют на результат: запросы к БД, изменение данных и настроек, вывод, файловая система, HTTP-запросы, запуск процессов, десериализация, `include`/`require`, перенаправления, отправка почты.

Если путь разобран не до конца — «выполнена частично» с указанием границы (например, «не прослежен вызов в сервис `Importer::run`»).

### Полнота реестра

- Найденное статическим поиском — это M, а не гарантированно полный список.
- Регистрации, которые нельзя установить статически (динамические имена хуков и маршрутов, регистрация в циклах, через собственный фреймворк или конфигурацию), указываются отдельно как ограничение. Если обработчик найден, а точное имя нет, запись вносится с пометкой «имя динамическое».
- Для `scope: diff` и `scope: feature` в реестр входят точки входа из охвата и точки входа, чьи обработчики затронуты изменением или фичей. Покрытие считается от этого набора, а не от всего проекта; это указывается в отчёте.

## 2. Проверки по типам точек входа

Для каждой записи реестра применяются вопросы её типа и сквозные проверки потоков данных (раздел 3).

### AJAX и admin-post

- **Доступность.** `nopriv`-вариант — доступна без входа. Только `wp_ajax_`/`admin_post_` — любой авторизованный пользователь, включая subscriber и, если включена регистрация, кого угодно. Права определяются только проверками внутри обработчика.
- **Авторизация.** `current_user_can()` с capability, соответствующей действию, до значимой операции. `is_admin()` проверкой прав не является (истинно для любого запроса к `admin-ajax.php`). `is_user_logged_in()` — только аутентификация.
- **Владение объектом.** Если действие над объектом по ID из запроса — проверка права на этот конкретный объект (`current_user_can( 'edit_post', $id )`, сравнение владельца), а не только общей capability.
- **CSRF.** `check_ajax_referer()` / `check_admin_referer()` / `wp_verify_nonce()` для действий, изменяющих состояние. Результат `wp_verify_nonce()` проверяется (функция не завершает выполнение). `check_ajax_referer( $action, $arg, false )` без проверки результата — не защищает. Nonce не является авторизацией: он не заменяет `current_user_can`.
- **Перенаправление** (admin-post): `wp_safe_redirect()` или проверка цели для URL из запроса; `exit` после редиректа.
- **Ответ.** Не раскрываются данные сверх прав пользователя.

### REST

- **`permission_callback`.** Задан для каждого маршрута и метода. `__return_true` — маршрут публичный: допустимо только если операция и данные действительно публичны (по коду и документации проекта); иначе — находка. Отсутствие `permission_callback` — маршрут публичный, WP выдаёт `_doing_it_wrong`.
- **Соответствие права действию.** Право в `permission_callback` соответствует операции в обработчике (например, проверка `read` для маршрута, удаляющего данные, — нарушение). Для разных методов на одном маршруте — разные проверки, если операции разные.
- **Владение объектом.** Для маршрутов с ID в пути или параметрах — проверка права на конкретный объект в `permission_callback` или обработчике.
- **Валидация `args`.** `type`, `enum`, `required`, `validate_callback`, `sanitize_callback`; параметры, используемые без объявления в `args`, получают произвольный ввод.
- **Ответ.** Не возвращаются чувствительные поля (хеши паролей, email, токены, приватные мета) пользователям без права на них; учитывается `context`.

### Обработчики на ранних хуках

- Кто может вызвать: обработчики `init`, `wp_loaded`, `template_redirect`, `parse_request` выполняются для любого посетителя; `admin_init` — также для неавторизованных запросов к `admin-ajax.php` и `admin-post.php`.
- Проверки прав и nonce внутри обработчика до значимой операции, по тем же правилам, что AJAX.

### Страницы администрирования

- Право на показ страницы (`capability` в `add_*_page`) не защищает обработку отправленной формы, если обработка выполняется на хуке, срабатывающем до проверки (например, `admin_init`) или вне callback-а страницы. Проверяется право на действие в месте обработки.
- Nonce при обработке отправки.
- `register_setting`, сохранение формы через `options.php`: значение обрабатывается только `sanitize_callback` (через фильтр `sanitize_option_{$option}`). Объявленный `type` при таком сохранении не проверяет и не приводит значение — он используется схемой REST. Без `sanitize_callback` или эквивалентного фильтра значение сохраняется как пришло.
- `register_setting` с `show_in_rest`: отдельно проверить схему (`type`, `show_in_rest.schema`) — она валидирует значение при записи через `/wp/v2/settings`, но не при сохранении формы.
- Право на сохранение настроек Settings API задаётся `option_page_capability_{$option_group}` (по умолчанию `manage_options`).

### Шорткоды и блоки

- Атрибуты шорткода задаёт любой пользователь, способный редактировать контент (contributor и выше). Атрибуты и содержимое — недоверенный ввод.
- Вывод экранируется по контексту (`esc_html`, `esc_attr`, `esc_url`, `wp_kses_post`); атрибуты не попадают без экранирования в HTML, JS, URL, SQL.
- Шорткод/блок не раскрывает данные сверх прав текущего посетителя (например, вывод приватных записей по ID из атрибута).
- Для блоков: атрибуты из `block.json` с `source` — те же правила; `render.php` получает `$attributes`, `$content`, `$block`.

### Шаблоны фронтенда

- Доступ к самой записи ядро обеспечивает основным запросом (статус, право читать приватные). Защиту её содержимого — только внутри своих функций: пароль проверяется в `get_the_content()` и `get_the_excerpt()`. Данные объекта, которые шаблон или компонент выводит напрямую, этой защиты не получают — см. раздел 3, «Неявные защиты платформы». Утверждение «доступ обеспечивает WordPress» без разбора конкретного вывода проверкой не является.
- Для каждого вывода данных объекта: источник (поле записи, мета, связанный объект), кто мог его записать, экранирование по контексту, применимость неявных защит.
- Собственные запросы в шаблоне (`WP_Query`, `get_posts`, `get_post` по ID из ввода): статус и права, параметры из `query_vars` и `$_GET`.
- Учёт: семейство шаблонов (одна иерархия и общие компоненты) можно вносить одной записью реестра. «Пройдена» ставится, когда разобран каждый вывод данных объекта в нём; иначе — «выполнена частично» с перечнем неразобранных выводов.

### Данные в REST ядра

- `show_in_rest => true` у CPT/таксономии открывает данные через `/wp/v2/` по правилам capabilities типа: проверить, что `capability_type`/`capabilities` и `public`/`publicly_queryable` соответствуют чувствительности данных.
- `register_meta` с `show_in_rest`: мета без префикса `_` редактируются при наличии права на объект, если `auth_callback` не задан иначе; `auth_callback => '__return_true'` — разрешает изменение любому, кто может редактировать объект. Проверить, не открываются ли чувствительные мета на чтение или запись.

### Изменение модели прав

- Фильтры `map_meta_cap`, `user_has_cap` не выдают capability шире задуманного: проверить условия (тип объекта, владелец, роль) и ветки по умолчанию.
- `authenticate`, `determine_current_user`: собственная аутентификация (токены, API-ключи, SSO) — сравнение секретов `hash_equals`, отсутствие обхода при пустом значении, корректный возврат `WP_Error`/`null`.
- `add_role`/`add_cap` при активации — не выдают ролям лишних capabilities (особенно `unfiltered_html`, `edit_users`, `promote_users`, `manage_options`).

### Загрузка файлов

- Права на загрузку (`upload_files` или специфичная capability) и nonce.
- Тип проверяется по содержимому и расширению средствами WP (`wp_handle_upload` с `test_type`, `wp_check_filetype_and_ext`), а не по `$_FILES[...]['type']` от клиента.
- Фильтр `upload_mimes` не разрешает исполняемые или опасные типы (`php`, `phtml`, `svg` без санитизации, `html`).
- Путь сохранения не формируется из пользовательского ввода без нормализации (path traversal); файлы не сохраняются в исполняемые каталоги вне uploads.

### Собственные URL

- Обработчик `template_redirect`/`parse_request` для rewrite-правила или endpoint — те же проверки прав и потоков данных, что у других точек входа; значения `query_vars` — недоверенный ввод.

### XML-RPC и Heartbeat

- Добавленные методы XML-RPC проверяют аутентификацию (`$this->login()` / `wp_xmlrpc_server::login`) и права.
- `heartbeat_received` выполняется для авторизованных; `heartbeat_nopriv_received` — для всех. Возвращаемые данные соответствуют правам.

### Cron

- Источник аргументов события: если аргументы формируются из пользовательского ввода при планировании, они проверяются в обработчике.
- Обработчик выполняется без текущего пользователя (`get_current_user_id() === 0`): проверки `current_user_can` в нём не работают как ограничение; доступ к планированию — точка контроля.
- WP-Cron запускается любым посетителем через `wp-cron.php`: тяжёлые или повторяемые операции оцениваются с учётом этого (пересечение с `reliability` REL-CHK-8 — не дублировать).

### WP-CLI

- Выполняется с правами системного пользователя; права WP не являются ограничением. Проверяются обработка аргументов (передача в SQL, файловые пути, `eval`, shell) и последствия ошибочного вызова: массовое изменение или удаление без подтверждения (`WP_CLI::confirm`, `--yes`) или `--dry-run`, когда операция необратима.

### Прямой доступ к файлам

- Файл без проверки `ABSPATH`, выполняющий код при прямом запросе: что выполняется (вывод с путями — раскрытие информации; обработка ввода вне WP — обход всех проверок; fatal error с путём — раскрытие при `display_errors`).
- Файлы, содержащие только объявления классов и функций, при прямом запросе обычно не выполняют значимого кода — фиксируется как рекомендация, не находка, если не показан эффект.

## 3. Сквозные проверки потоков данных

Применяются на пути от каждой точки входа до значимых операций.

| Операция | Требование | Типовые нарушения |
|---|---|---|
| SQL | `$wpdb->prepare()` с плейсхолдерами для значений; имена таблиц/колонок и `ORDER BY` — только из whitelist; `esc_like()` для `LIKE` | Конкатенация ввода в запрос; `prepare` с уже подставленной строкой; `esc_sql` без кавычек вокруг значения; `intval` после использования |
| Вывод HTML | Экранирование в момент вывода по контексту: `esc_html`, `esc_attr`, `esc_url`, `esc_js`/`wp_json_encode`, `wp_kses`/`wp_kses_post`; `esc_textarea` | Вывод санитизированного, но не экранированного значения; `esc_html` в атрибуте href; `wp_kses_post` для атрибута |
| Запись данных | Санитизация по типу: `sanitize_text_field`, `sanitize_key`, `absint`, `sanitize_email`, `esc_url_raw`/`sanitize_url`, `wp_kses_post`; `wp_unslash` перед санитизацией суперглобалов | Запись сырого `$_POST` в опции/мета; массовое присваивание всех полей запроса |
| Файловая система | Путь не из ввода либо нормализован и проверен на нахождение в разрешённом каталоге (`realpath` + префикс, `validate_file`); `WP_Filesystem` для записи | `../` в имени файла; запись в каталог плагина |
| `include`/`require` | Путь не зависит от ввода или выбирается из whitelist | LFI через параметр шаблона |
| Десериализация | Нет `unserialize`/`maybe_unserialize` на данных, контролируемых пользователем | Object injection через cookie, параметр, мета, заполняемую пользователем |
| HTTP-запросы | URL из ввода — `wp_safe_remote_*` и whitelist хостов | SSRF через `wp_remote_get( $_GET['url'] )` |
| Процессы и eval | Нет `eval`, `assert` со строкой, `create_function`, `preg_replace` с `/e`; `exec`/`shell_exec`/`system`/`proc_open` — только с `escapeshellarg` и без ввода в имени команды | Командная инъекция |
| Перенаправления | `wp_safe_redirect` или `wp_validate_redirect` для URL из ввода | Open redirect через `redirect_to` |
| Почта | Заголовки не содержат пользовательский ввод без очистки переводов строк; получатель не задаётся посетителем произвольно | Использование формы как релея |
| Секреты и сравнение | `hash_equals` для токенов; секреты не выводятся и не логируются; случайные значения — `wp_generate_password`/`random_bytes` | `==` для токенов; `rand()`/`uniqid()` для токенов |

Источники недоверенных данных: суперглобалы, параметры REST, атрибуты шорткодов и блоков, `query_vars`, содержимое загруженных файлов, ответы внешних сервисов, данные, записанные пользователями с меньшими правами (мета, комментарии, контент, опции, изменяемые не только администраторами) — включая stored XSS при выводе в админке.

### Неявные защиты платформы

Часть защит WordPress применяет не везде, а внутри определённых функций. Код проекта, читающий те же данные напрямую, их обходит. Проверка применяется на всех путях вывода данных объекта: шаблоны фронтенда и их компоненты, шорткоды, блоки, REST-поля, фиды. Поведение функций ядра сверяется с локальным `wp-includes/` (см. `SKILL.md`, «Общие правила проверки»).

| Защита | Где ядро её применяет | Типовой обход в коде проекта |
|---|---|---|
| Пароль записи | `post_password_required()`; применяется в `get_the_content()`, `get_the_excerpt()` и при выдаче content/excerpt в REST | Вывод мета и полей (ACF/SCF), `$post->post_content`, вложений и других данных записи без проверки пароля; вывод до вызова `the_content()` |
| Статус записи и право чтения | Основной запрос и `WP_Query` учитывают статус и `read_private_posts`; `get_post()`, `get_post_meta()`, `WP_Query` с явным `post_status` права не проверяют | Вывод записи по ID из ввода (атрибут шорткода, параметр AJAX или REST, query var) без `current_user_can( 'read_post', $id )` или `is_post_publicly_viewable()`: черновики, приватные записи, непубличные типы |
| kses при сохранении | `kses_init_filters()` для пользователя без `unfiltered_html`: контент, заголовок, excerpt, комментарии. Мета ядро не фильтрует: только `sanitize_callback` из `register_meta` или обработка плагина полей | Мета или опция, заполняемая пользователем без `unfiltered_html`, выводится как HTML; декодирование сущностей после kses (`html_entity_decode`, `wp_specialchars_decode`, вставка через `innerHTML` на клиенте) |
| Ограничение, реализованное проектом в шаблоне | Не защита ядра: действует только в этом шаблоне | Содержимое, скрытое проверкой в шаблоне (роль, подписка, собственный пароль), отдаётся через REST, RSS, поиск, oEmbed, `?p=ID`, страницы вложений. Основание — собственное ограничение проекта, видимое в коде |

Видимость данных через REST ядра и мета-capabilities проверяются в разделе 2 («Данные в REST ядра», «Изменение модели прав», «Владение объектом»).

Условие прохождения: на каждом найденном пути вывода защищаемых данных защита либо применена, либо легитимно не требуется. В покрытии перечислить пути вывода, вошедшие в проверку.

## 4. Доказательство

Подтверждённая уязвимость требует достижимого пути выполнения от точки входа до последствия:

- точка входа (ID реестра) и кто может её вызвать;
- путь через функции с файлами и строками;
- отсутствующая или обходимая проверка;
- значимая операция и последствие;
- необходимые права, конфигурация, действия пользователя.

Если путь не доведён до последствия, доступность точки входа неизвестна (динамическая регистрация) или ожидаемое ограничение доступа не установлено — гипотеза с указанием, чего не хватает и как её подтвердить. Подтверждение запросом к работающему сайту не выполняется.

## 5. Покрытие для отчёта

- Сводка «проверено N из M» по типам точек входа (N — со статусом «пройдена» или «обнаружено нарушение»).
- Полный реестр, сгруппированный по типам.
- Пути вывода, проверенные на неявные защиты платформы (раздел 3), со статусами.
- Ограничения полноты: способ поиска, динамические регистрации, точки входа со статусом «выполнена частично» и их границы, для `diff`/`feature` — от какого набора считается покрытие.
