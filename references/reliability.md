# Область reliability

Предмет: обработка ошибок и некорректного ввода, соблюдение контрактов API, управление ресурсами и состоянием при повторах и частичных отказах.
Результат: подтверждённые нарушения технических контрактов и инвариантов с указанием основания.

Проверка ведётся чтением кода. Команды проекта здесь не запускаются, работающий сайт не используется.

## Принципы

- Основание находки — контракт языка, платформы или API, техническое соглашение, зафиксированное в репозитории, либо техническая гарантия, установленная кодом проекта (признаки — `SKILL.md`, «Общие правила проверки»). Бизнес-логика и «правильность» поведения с точки зрения продукта не оцениваются.
- Отсутствие вызова или шаблона (нет `is_wp_error`, нет `try/catch`) само по себе не дефект. Дефект — достижимый путь, на котором нарушение контракта приводит к последствию: fatal error, потеря или порча данных, неверный результат для вызывающего кода, утечка ресурса.
- Повтор и частичный отказ оцениваются только при обоснованном техническом инварианте: контракт API, механизм повторной доставки (cron, webhook, очередь, повторная отправка формы), явно зафиксированная гарантия, техническая гарантия, установленная кодом проекта. Универсальные требования идемпотентности и атомарности всем операциям не приписываются.
- Последствие оценивается по фактическому поведению платформы: например, warning в PHP 8 при обращении к свойству `null` — не то же, что fatal error при вызове метода у `WP_Error`.

## Порядок прохода

1. Определить в охвате вызовы с нетривиальным контрактом возврата и точки, где внешние данные входят в код (переиспользовать реестр точек входа из `security`, если он уже составлен). Точка входа, признанная безопасной по `security` (CLI-скрипт, импорт и экспорт, cron, обработчик только для администратора), проходит проверки reliability наравне с остальными: ограничение круга вызывающих не отменяет обработку ошибок файловых операций, БД и API (REL-CHK-1, REL-CHK-2, REL-CHK-9).
2. Составить список механизмов с состоянием (REL-CHK-11) и повторных запусков (REL-CHK-12). Эти проверки идут не от отдельного вызова, а от механизма целиком: так находятся дефекты между компонентами, ветками и средами, которые не видны из одного места. Список дополняется по ходу чтения.
3. Для каждого места и механизма — проверки из списка ниже, применимые к нему. Браузерный код проверяется наравне с PHP, по контрактам browser API.
4. Для кандидата — проследить путь до последствия и найти основание (документация функции, сигнатура, исходник ядра, соглашение проекта).

## Проверки

### REL-CHK-1. Результат, который может быть `WP_Error`

- Предмет: использование результата функций, возвращающих `WP_Error` (по контракту или при `$wp_error = true`).
- Когда применима: в охвате есть вызовы `wp_insert_post`/`wp_update_post` с `$wp_error = true`, `wp_insert_term`, `wp_update_term`, `wp_insert_user`, `wp_update_user`, `wp_create_user`, `wp_remote_get/post/request`, `wp_safe_remote_*`, `get_term`/`get_terms` (с невалидной таксономией), `wp_set_object_terms`, `media_handle_upload`, `media_handle_sideload`, `download_url`, `wp_insert_category`, `rest_do_request`/обработчики, вызываемые проектом, собственные функции проекта, документированно возвращающие `WP_Error`.
- Основание: документированный тип возврата функции.
- Способ: проследить использование результата до первого обращения как к успешному значению (индекс массива, свойство, арифметика, передача в функцию, ожидающую ID).
- Условие прохождения: ошибочный результат обрабатывается до использования или путь с ошибкой недостижим.
- Отсутствие доказательств: если нельзя установить, достижима ли ошибка, — гипотеза с указанием условия ошибки.

### REL-CHK-2. Отказ, сообщаемый возвращаемым значением

- Предмет: вызовы, которые сообщают об отказе возвращаемым значением (`false`, `null`, `0`, пустой результат), — при чтении и при записи. Критерий — контракт функции; перечень ниже — примеры, а не граница проверки.
- Когда применима: чтение — `get_post`, `get_user_by`, `get_userdata`, `get_term_by`, `get_option` (default `false`), `get_post_meta`/`get_user_meta` с `$single`, `wp_get_attachment_*`, методы `$wpdb` (контракты различаются — см. REL-CHK-9), `json_decode`, `file_get_contents`, `fopen`, `strpos`, `wp_cache_get` (параметр `$found`), `get_transient`; запись — `update_*_meta`/`update_option` (`false` и при неизменном значении), `wp_insert_post` без `$wp_error` (`0`), `copy`, `file_put_contents`, `wp_mkdir_p`.
- Основание: документированный тип возврата PHP или WP.
- Способ: для каждого вызова — что получат вызывающий код и следующий шаг при отказе: `false` как объект или ID, отказ записи, выданный за успех (ответ REST, `WP_CLI::success`, notice), следующий шаг без записанных данных. Проверить различение ошибки и легитимного «пусто»/`0`.
- Условие прохождения: отказ различается там, где это влияет на результат.
- Отсутствие доказательств: гипотеза.

### REL-CHK-3. Ответы внешних HTTP-запросов

- Предмет: обработка результата `wp_remote_*`.
- Когда применима: в охвате есть HTTP-запросы.
- Основание: контракт HTTP API (`WP_Error` при транспортной ошибке; код ответа не проверяется автоматически).
- Способ: проверить обработку `WP_Error`, проверку кода ответа (`wp_remote_retrieve_response_code`) до разбора тела, обработку невалидного тела (`json_decode` → `null`), наличие таймаута при синхронном запросе в пользовательском запросе (по умолчанию 5 с — только если проект явно его увеличивает или ставит 0).
- Условие прохождения: транспортная ошибка, неуспешный код и невалидное тело не приводят к использованию неверных данных или fatal error.
- Отсутствие доказательств: формат ответа внешнего сервиса неизвестен — недостаток технического контекста.

### REL-CHK-4. Некорректный и отсутствующий ввод

- Предмет: использование `$_GET`/`$_POST`/`$_REQUEST`/`$_COOKIE`/`$_SERVER`, параметров REST, атрибутов шорткодов и блоков, аргументов CLI и cron.
- Когда применима: в охвате есть точки входа.
- Основание: правила PHP (неопределённый индекс, типы), контракт `WP_REST_Request` и `args` (`type`, `required`, `validate_callback`), `shortcode_atts`.
- Способ: проверить, что отсутствующий ключ, массив вместо строки, пустая строка, нечисловое значение не приводят к fatal error (`TypeError` в строго типизированном коде, вызов функции строк от массива) или к записи неверных данных.
- Условие прохождения: ввод валидируется или приводится до значимого использования; некорректный ввод даёт контролируемую ошибку.
- Отсутствие доказательств: для REST — если валидация вынесена в схему, проверить схему; если схема динамическая и её нельзя установить — ограничение.

### REL-CHK-5. Контракт REST-ответа и хуков

- Предмет: значения, возвращаемые обработчиками REST, фильтрами и callback-ами.
- Когда применима: в охвате есть `register_rest_route`, `add_filter`, `register_setting` с `sanitize_callback`, callback-и сортировки, `pre_*` фильтры.
- Основание: контракт API — фильтр обязан вернуть значение (иначе `null` подменяет данные), `permission_callback` возвращает `bool|WP_Error`, REST-обработчик — `WP_REST_Response|WP_Error|mixed`, `sanitize_callback` — санитизированное значение, а не `false` для «отклонить».
- Способ: проверить все пути возврата callback-а, включая ранние `return;`.
- Условие прохождения: на всех путях возвращается значение допустимого типа.
- Отсутствие доказательств: —

### REL-CHK-6. Порядок загрузки и доступность API

- Предмет: вызов функций WP до того, как они доступны.
- Когда применима: код выполняется при подключении файла или на ранних хуках (`plugins_loaded`, `muplugins_loaded`, `setup_theme`).
- Основание: порядок загрузки WordPress — например, `wp_get_current_user`/`current_user_can` до `plugins_loaded` (pluggable), `register_post_type` вне `init`, `is_*` conditional tags до `parse_query`/`wp`, переводы (`__()`) до `init` (WP 6.7+ выдаёт `_doing_it_wrong` для just-in-time загрузки ранее `init`).
- Способ: проследить, где и когда выполняется вызов.
- Условие прохождения: API вызывается на подходящем хуке.
- Отсутствие доказательств: —

### REL-CHK-7. Ресурсы и состояние

- Предмет: открытые файлы, блокировки, временные файлы, изменённое глобальное состояние.
- Когда применима: в охвате есть `fopen`, `tmpfile`, `download_url` (временный файл), `switch_to_blog`, `wp_suspend_cache_invalidation`, `remove_filter`/`add_filter` вокруг операции, изменение глобальных `$post`/`$wp_query` (`setup_postdata`, `query_posts`), собственные блокировки через опции/транзиенты, `set_time_limit`, `ignore_user_abort`.
- Основание: контракт API — `switch_to_blog` требует `restore_current_blog`, `setup_postdata`/кастомный `WP_Query` — `wp_reset_postdata`, `query_posts` — `wp_reset_query`, временный файл `download_url` удаляется вызывающим.
- Способ: проверить восстановление состояния и освобождение ресурса на всех путях, включая ранний `return` и исключения.
- Условие прохождения: состояние восстановлено на всех достижимых путях.
- Отсутствие доказательств: —

### REL-CHK-8. Повторы и частичные отказы

- Предмет: операции, которые по техническому механизму могут выполниться повторно или прерваться на середине.
- Когда применима: только при наличии инварианта — обработчики cron (повторный запуск при пересечении, ручной запуск), webhook-и внешних сервисов с повторной доставкой, Action Scheduler, повторная отправка формы, многошаговые операции, явно описанные в проекте как атомарные, хуки активации/обновления, выполняемые повторно, `wp_schedule_event` в коде, выполняющемся на каждом запросе.
- Основание: документированное поведение механизма, зафиксированная в проекте гарантия или техническая гарантия, установленная кодом проекта (код после операции полагается на её полное выполнение).
- Способ: проверить, что повтор не нарушает инвариант (дубликаты записей, двойное списание, повторная отправка писем, накопление событий cron без `wp_next_scheduled`), а частичный отказ — не оставляет состояние, нарушающее зафиксированную гарантию.
- Условие прохождения: инвариант сохраняется при повторе или прерывании.
- Отсутствие доказательств: инварианта нет — проверка «неприменима» с причиной; само отсутствие идемпотентности не является находкой.

### REL-CHK-9. Работа с БД

- Предмет: собственные запросы и таблицы.
- Когда применима: в охвате есть `$wpdb` или `dbDelta`.
- Основание: контракты методов `$wpdb` (различаются, см. таблицу ниже), требования `dbDelta` к формату `CREATE TABLE` (два пробела перед `PRIMARY KEY`, каждое поле на своей строке, `KEY` вместо `INDEX`), `$wpdb->prefix` и `get_charset_collate()`.
- Способ: проверить обработку ошибки там, где она влияет на результат (например, использование `insert_id` после неудачного `insert`), корректность схемы для `dbDelta`, использование префикса.
- Условие прохождения: ошибка БД не приводит к неверным данным, схема соответствует требованиям `dbDelta`.
- Отсутствие доказательств: —

Результаты методов `$wpdb` при ошибке SQL и при отсутствии строк:

| Метод | Ошибка SQL | Нет строк | Как различить |
|---|---|---|---|
| `query()` | `false` | `0` (число затронутых строк) | строгое сравнение с `false` |
| `insert()`, `update()`, `replace()`, `delete()` | `false` | `0` | строгое сравнение с `false`; `insert_id` валиден только после успешного `insert` |
| `get_results()` | пустой массив | пустой массив | только `$wpdb->last_error` |
| `get_col()` | пустой массив | пустой массив | только `$wpdb->last_error` |
| `get_row()` | `null` | `null` | только `$wpdb->last_error` |
| `get_var()` | `null` | `null` | только `$wpdb->last_error` |

Проверка только на `false` у `get_*` методов ошибку не обнаруживает. Находка — только если различение ошибки и «пусто» влияет на результат (например, пустой результат при ошибке трактуется как «записей нет» и запускает создание дубликата или удаление).

Проверки SQL-инъекций относятся к `security`, не дублируются здесь.

### REL-CHK-10. Соглашения проекта об обработке ошибок

- Предмет: собственные правила проекта (исключения vs `WP_Error`, логирование, формат ответов).
- Когда применима: соглашение зафиксировано в репозитории.
- Основание: документ или инструкция проекта с указанием источника.
- Способ: сверить код охвата с соглашением.
- Условие прохождения: нарушений нет.
- Отсутствие доказательств: соглашение не зафиксировано — «неприменима».

### REL-CHK-11. Механизмы с состоянием на стыках компонентов

- Предмет: механизм — код в нескольких местах, который производит, хранит, преобразует и потребляет одно состояние.
- Когда применима: механизм отвечает хотя бы одному признаку:
  - данные пересекают границу компонентов, хранилищ или сред: опция или мета → шаблон, PHP → JS (data-атрибут, `wp_localize_script`, inline JSON), cookie ↔ localStorage, транзиент или кэш ↔ источник, сервер ↔ клиентская синхронизация;
  - данные меняют формат по пути: сериализация, JSON, кодирование и декодирование сущностей;
  - в механизме есть синхронизация, восстановление, повтор, reload или redirect.
- Основание: контракт использованного API или техническая гарантия, установленная кодом проекта (`SKILL.md`, «Общие правила проверки»): потребитель в коде полагается на результат производителя. Например: код читает одно хранилище как согласованное с другим → синхронизация обеспечивает согласованность во всех состояниях, где этот код выполняется; JS ищет элемент разметки, чтобы запустить восстановление → сервер выводит его в тех ветках, которые требуют восстановления. Желаемое поведение без опирающегося на него потребителя и продуктовые ожидания основанием не являются.
- Способ:
  1. Карта: производители и потребители состояния, места хранения, преобразования формата, условия запуска каждого участника — с файлами и строками.
  2. Значимые состояния выводятся из ветвлений кода и контрактов API участников, а не из общего списка. Типичные источники: ветка «пусто / не найдено» у потребителя; хранилища расходятся или одно из них пустое; запись завершилась исключением, тихим отказом или частично; разметка, которую ожидает JS, есть не во всех серверных ветках; соседний модуль упал раньше при общей инициализации.
  3. Для каждого достижимого состояния проследить поведение каждого участника и проверить инвариант.
- Стоимость: карта строится только для механизмов, отвечающих признакам выше, а не для всех потоков данных проекта. Для `global` это ограничивает проход; механизмы без признаков проверяются обычными REL-CHK.
- Условие прохождения: инвариант сохраняется во всех достижимых состояниях карты.
- Отсутствие доказательств: инвариант не следует из кода или контракта — «неприменима» с причиной; достижимость состояния не установлена — гипотеза с условием.

Пример метода: обработчик кэширует ответ внешнего API в транзиент, а несколько шаблонов читают транзиент как готовый массив данных. В ветке ошибки источника производитель сохраняет в тот же ключ `WP_Error` или пустой массив на полный срок кэша. Потребители рассчитаны только на массив данных: в этом состоянии карты — fatal error или пустой вывод до истечения срока, хотя источник уже снова доступен.

### REL-CHK-12. Завершение повторных запусков

- Предмет: код, который снова запускает сам себя или ту же операцию: reload или redirect после записи, retry, перепланирование cron или Action Scheduler из обработчика, рекурсивный хук (`save_post` → `wp_update_post`), повторный клиентский запрос до успеха.
- Когда применима: в охвате есть такой код.
- Основание: условие завершения. Повторный запуск оправдан изменением состояния, которое делает условие запуска ложным при следующем проходе.
- Способ: установить условие следующего запуска и что его меняет; проверить, меняется ли оно при отказе записи или при неизменном значении. Учитывать API, которые не сообщают об отказе или сообщают неочевидно:
  - присваивание `document.cookie` результата не возвращает; браузер молча отвергает cookie сверх лимита размера (в Chromium — 4096 байт на имя и значение) или с недопустимыми атрибутами;
  - `localStorage.setItem` и `getItem` бросают исключение при переполнении или запрете хранилища;
  - `update_option` и `update_post_meta` возвращают `false` и при ошибке, и при неизменном значении.
- Условие прохождения: при отказе записи или неизменном состоянии повтор не идёт бесконечно — есть проверка результата, ограничение числа попыток, маркер попытки, `remove_action` перед рекурсивным вызовом или аналог.
- Отсутствие доказательств: нельзя установить, может ли запись не выполниться, — гипотеза с условием отказа.

Отличие от REL-CHK-8: там — сохранение инварианта данных при повторе, здесь — завершение самого повтора.

## Доказательство

- Ошибка выполнения: достижимый путь от точки входа или вызова до последствия, с файлами и строками и условием, при котором API возвращает ошибочное значение.
- Нарушение соглашения: правило, его источник в проекте, место нарушения.

Если путь не доведён до последствия или условие ошибки не установлено — гипотеза с указанием, чего не хватает.

## Покрытие для отчёта

По каждой проверке REL-CHK — статус по шкале и, для «выполнена частично» и «не проверена», границы и причина. Перечислить, какие места (функции, точки входа) вошли в проход.

Для REL-CHK-11 и REL-CHK-12 — список механизмов и повторных запусков; для каждого — участники, рассмотренные состояния и результат. Статус «пройдена» без перечня рассмотренных состояний не ставится.
