# Отчёт

Полный отчёт сохраняется в Markdown-файл на русском. По умолчанию — `docs/reviews/wp-project-review-YYYY-MM-DD-HHMMSS.md` относительно корня проверяемого проекта, с датой и временем текущего запуска. Явно указанный пользователем путь имеет приоритет; относительный путь также считается от корня проверяемого проекта. Необходимый каталог создаётся автоматически. Дополнительное подтверждение сохранения не требуется.

Существующий файл не перезаписывать без явного указания пользователя: при совпадении имени добавить числовой суффикс перед `.md`. После записи проверить, что файл существует и содержит полный отчёт. Если сохранение недоступно, сообщить причину и не заявлять, что отчёт сохранён; полный текст автоматически в чат не переносить.

Затем собрать HTML-копию: `python3 <каталог скилла>/scripts/report-html.py <отчёт.md>` — рядом появится `<отчёт>.html`. Источник HTML — Markdown; разметка находок — строго по шаблону ниже. Если `python3` нет или скрипт завершился ошибкой — указать это в ответе.

В финальном ответе — пути к Markdown- и HTML-файлам, краткий итог по находкам и существенные ограничения покрытия. Полный отчёт в чат или терминал не дублировать. Промежуточный результат при вынужденной остановке сохраняется по тем же правилам с явной отметкой о незавершённости. Другие файлы проекта не изменяются, кроме HTML-копии, допустимых кэшей и временных файлов инструментов.

Вердикта о готовности к релизу отчёт не содержит — его заменяет итог по находкам и покрытию. P0/P1/P2 и решение о блокировке релиза не используются: они требуют отдельно согласованных правил проекта и не выводятся из уровня важности.

Если все запрошенные области не реализованы, отчёт не выдаётся — только уведомление об отсутствии поддержки (см. `SKILL.md`).

## Классификации

### Статус проверки

- Пройдена.
- Обнаружено нарушение.
- Неприменима — с причиной.
- Не проверена — с причиной.
- Выполнена частично — с указанием границ.

### Тип замечания

- **Подтверждённый дефект** — есть проверяемое доказательство нужного вида.
- **Гипотеза, требующая проверки** — доказательства не хватает; указывается, чего именно и как подтвердить.
- **Недостаток технического контекста** — отсутствует основание для вывода; сам по себе не является дефектом.
- **Рекомендация** — улучшение без установленного дефекта.

### Важность

Шкала едина для всех областей. Важность назначается конкретной находке, а не пункту чек-листа.

| Уровень | Критерий |
|---|---|
| Critical | Компрометация системы, массовая утечка, необратимая потеря критичных данных либо сопоставимый ущерб |
| High | Существенное нарушение доступа, целостности данных или работоспособности затронутой функциональности |
| Medium | Ошибка с ограниченным ущербом или нарушение части функциональности при наличии приемлемого обходного пути |
| Low | Незначительный дефект без существенного влияния на доступ, данные и работоспособность |

Правила:

- Уровень определяется ожидаемым ущербом. Для выбранного уровня обосновываются последствия, масштаб и условия возникновения, включая необходимые права и конфигурацию.
- Требуемые права, специфичная конфигурация и необходимое действие пользователя учитываются, но не понижают уровень автоматически.
- Если требуемые права уже легитимно дают тот же результат, находка снимается.
- Название класса ошибки («XSS», «SQL-инъекция») само по себе не определяет важность.
- Для гипотезы важность предварительная и помечается так; предполагаемый ущерб не делает её подтверждённым дефектом.
- Если данных для оценки недостаточно — важность «не определена» с объяснением причины.
- Рекомендации и недостаток технического контекста уровня важности не получают.

## Доказательство по типу дефекта

| Тип дефекта | Требуемое доказательство |
|---|---|
| Ошибка выполнения или эксплуатируемая уязвимость | Достижимый путь выполнения от точки входа до последствия |
| Нарушение явно принятого стандарта или соглашения | Правило, его источник в проекте и место нарушения |
| Несовместимость конфигурации или зависимостей | Конфликтующие значения или версии и источник требования |
| Результат инструмента | Разобранное сообщение с контекстом |

Без доказательства нужного вида находка остаётся гипотезой.

## ID

- Находки: `TOOL-N`, `REL-N`, `SEC-N` — уникальны в пределах отчёта, нумерация по порядку появления в разделе «Находки».
- Точки входа security: `E-N`.
- Проверки: `TOOL-CHK-N`, `REL-CHK-N`, `SEC-CHK-N` — постоянные ID из references, не нумеруются заново в отчёте и не совпадают с ID находок (`SEC-2` — находка, `SEC-CHK-2` — проверка).
- Рекомендации: `REC-N`.
- Одна причина — одна находка. Если дефект виден из нескольких областей, он оформляется в наиболее подходящей, остальные области ссылаются на его ID.

## Структура отчёта

```markdown
# Ревью WordPress-проекта: <имя объекта>

## 1. Параметры проверки

- Дата: YYYY-MM-DD
- Объект: `target: plugin` — `my-plugin.php`, заголовок `Plugin Name: …`
- Собственный код: … (для `site` и смешанных репозиториев — границы и основание)
- Охват: `scope: diff`, `base: main` (merge-base `abc1234`), HEAD `def5678`, незакоммиченные изменения в охвате: есть / нет
- Области:
  - запрошены: …
  - выполнены: …
  - не выполнены: `architecture` — не реализована в текущей версии скилла; …

## 2. Итог

Несколько строк, без новых выводов:
- находки: подтверждённые дефекты — Critical N, High N, Medium N, Low N; гипотезы — …; недостаток технического контекста — N;
- проверки со статусом «не проверена»: …; «выполнена частично»: …;
- главные ограничения: …

## 3. Находки

### Подтверждённые дефекты
(по убыванию важности)

### Гипотезы
(по убыванию предварительной важности)

### Недостаток технического контекста
(если есть; без важности)

## 4. Покрытие

### tooling
Сводка запусков (формат — `tooling.md`, п. 8) и статусы TOOL-CHK.

### reliability
Статусы REL-CHK, места, вошедшие в проход. Механизмы и повторные запуски (REL-CHK-11, REL-CHK-12): участники, рассмотренные состояния, результат.

### security
- Проверено N из M по типам точек входа (таблица).
- Реестр, сгруппированный по типам.
- Статусы SEC-CHK-1 и SEC-CHK-2; для SEC-CHK-2 — пути вывода со статусами.
- Ограничения полноты реестра и способ поиска.

## 5. Ограничения и открытые вопросы

- Непроверенное с причинами.
- Для `diff` и tooling: возможные существовавшие ошибки; пропуски вне изменённых файлов.
- Вопросы, ответ на которые изменит вывод.

## 6. Рекомендации

Без уровня важности, отдельно от находок.
```

Разделы выполненных областей присутствуют всегда, даже если находок нет. Невыполненные области не получают разделов покрытия — только строку в «Параметрах» и «Ограничениях».

## Шаблон находки

```markdown
#### SEC-1. <суть одной фразой>

- **Область / тип / важность:** security · подтверждённый дефект · High
- **Место:** `includes/class-ajax.php:42`, `My_Ajax::delete_item()`, `wp_ajax_my_delete` (E-3)
- **Основание:** правило платформы / контракт API / соглашение репозитория (источник)
- **Доказательство:** путь выполнения / правило и место / конфликтующие значения / разобранное сообщение инструмента
- **Условия:** необходимые права, конфигурация, действия пользователя
- **Последствия и обоснование важности:** …
- **Направление исправления:** без готового патча
```

Для гипотезы добавляется:

```markdown
- **Чего не хватает:** …
- **Как подтвердить:** …
```

Номера строк указываются для проверяемого состояния кода; для `diff` — для текущего состояния, не для `base`.

## Сводка tooling

По каждому инструменту: команда, фактический охват запуска, результат, количество сообщений по правилам или категориям, ограничения покрытия. Сырой вывод не переносится. Находкой с типом и важностью становится только разобранное сообщение; неразобранные остаются в сводке без важности.

## Самопроверка перед выдачей

- Покрытие сверено с планом: доступная работа в выбранном охвате завершена. У каждого непроверенного остатка указаны конкретное препятствие и необходимое действие для продолжения; простая незавершённость не выдана за ограничение. Если проход вынужденно прерван, результат обозначен как промежуточный по правилам завершения `SKILL.md`.
- Все запрошенные области учтены: выполнены или перечислены как невыполненные с причиной.
- У каждой находки есть основание и доказательство нужного вида; без него — гипотеза.
- У каждой гипотезы указано, чего не хватает и как подтвердить.
- Важность не назначена рекомендациям и недостатку контекста; у каждой важности есть обоснование.
- Нет дубликатов между областями.
- Для security есть «N из M» и реестр; для tooling — фактический охват запусков.
- Полный отчёт сохранён и запись проверена; HTML-копия собрана или причина указана; в ответе пользователю указаны путь и краткий итог без дублирования отчёта.
